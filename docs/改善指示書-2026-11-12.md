## 0.5 入力済みのデータを壊さないための決まり【最優先・全項目に適用】

ユーザーの指示（2026-11-12）: **すでに入力されているデータが壊れないように配慮すること。**
本番では4施設が毎日入力している。以下は、どの項目よりも優先する。迷ったら実装を止めてユーザーに確認する。

### データの形

1. **追加だけ。** 新しい項目は「任意の項目を足す」形に限る。既存の項目の名前変更・削除・意味の変更・型の変更をしない。
2. **項目が無い＝従来どおり。** 新しい項目が入っていない古いデータで、画面・生成・出力が今と同じ結果になること。
3. **一括の書き換え（データ移行）をしない。** 既存の文書をまとめて書き直す処理・スクリプトは作らない。
   どうしても必要になったら、実装前に内容・対象件数・戻し方をユーザーに示して了承を取る。
4. **文書ID・参照を変えない。** 職員ID・勤務パターンID・`schedules/{年月}`・`leaveRequests` の「職員ID_日付」など、
   参照に使っている ID の作り方を変えない。
5. **引っ越しファイルの互換。** 以前に書き出したバックアップ（`facilityTransfer` 形式・自動バックアップ）が、
   改修後もそのまま読み込めること。形式を変える場合は、古い形式を読める状態を保つ。

### 書き込みの処理を直すとき（A4・C1・C2・C4・D7 が該当）

6. **1マスの保存は、そのマスだけを書く。** 今は `assignments.職員ID.日` のように項目を指定して更新している
   （`lib/firestore.ts` の `setAssignment` ほか）。これを `assignments` 全体の置き換えに変えない。
   全体を置き換えると、同時に入力しているほかの人のマスを消してしまう。
7. **`revision`（版）を上げる動きを保つ。** 採択時の「手直しを上書きしないか」の確認がこれに頼っている。
8. **まとめて入力（C1）は空いているマスだけ。** 入力済み・ロック済み・希望休の日は上書きしない。
   実行前に「何名・何マスに入れるか」を表示して確認し、1回の書き込みにまとめる（途中で止まって半端に残らない）。
9. **元に戻す（C2）は、自分が入れた値のままのときだけ戻す。** その後にほかの人が変えていたら戻さない。
10. **保存に失敗したら、画面を読み込み直して実際の状態を見せる**（今の動きを保つ）。保存できていないのに入ったように見せない。
11. 自動生成は、採択するまで勤務表を変えない（今の動きを保つ）。生成まわりの改修（B）で書いてよいのは案（`candidates`）だけ。

### 削除・無効化

12. A2・A3 は「止める・表示する」だけで、既存のデータを書き換えない。削除を止める判定に失敗した（読み込めなかった）ときは、
    **削除させない側**に倒す。
13. Excel 取込・旧データ取込・重複整理・施設データの読み込み（置き換え）の動きは、この指示書の対象外。触らない。

### `firestore.rules`

14. ルールを変える項目はこの指示書に無い。変える必要が出たら別フェーズにし、ユーザーの了承を取る。緩める方向の変更はしない。

### 確認の手順（フェーズごと）

15. **テスト:** 古い形のデータ（職種が単数の `jobTypeId`、`order` なし、`settings` 未作成、`baseRevision` の無い案、
    `editLock` なし、兼務行なし）を読んでも結果が変わらないことを、テストで確かめる。
16. **動作確認は dev で行う。** 本番では、確認のために勤務を入れたり消したりしない（見るだけ）。
17. **本番に反映する前:** ユーザーに、4施設それぞれ「施設・ユーザー管理 → 書き出す」でその日のバックアップを取ってもらう。
18. **本番に反映した後:** 各施設で当月と前月の勤務表を開き、職員の人数・違反の件数・個人別の集計が反映前と同じことを
    ユーザーと確かめる（反映前に数字を控えておく）。違っていたら、原因が分かるまで次へ進まない。
19. 見た目の変更（D）とファイルの分割（D7）は、保存処理の呼び出し方を変えない。変更の前後で、
    1マスの入力・ロック・行事・月の上限・採択の保存内容が同じであることを dev で確かめる。

## 1. 優先度A：不具合・事故の予防（小さく直せる。先に行う）

### A1. PCがダークモードだと、カードの中の文字が読めない【確認済み】

- 根拠: `src/index.css` は配色を明るい色に固定しているが、`src/App.css` に
  `@media (prefers-color-scheme: dark)` が3か所残っている（1157行・1205行・1702行付近）。
  OS がダークモードだと `.card` と `.modal-card` の背景だけ `#1f2320` になり、文字色 `#22271f` と重なって見えない。
  ログイン画面で再現（背景 `rgb(31,35,32)`・文字 `rgb(34,39,31)`）。
- やること: 3つの `@media (prefers-color-scheme: dark)` ブロックを削除する（ダークモード対応は C 系の配色整理の後に別途）。
- 完了条件: ブラウザのダークモード再現で、ログイン画面・シフト表・モーダル・トーストが明るい配色のまま読める。

### A2. 退職・削除した職員が、過去の月の勤務表から消える

- 根拠: `ShiftGridPage.tsx:191` などが「今、有効な職員」だけを表示する（`active !== false`）。
  同じ絞り込みが 希望休・有給休暇・月の上限・市の提出様式（`buildSubmissionRows.ts:55`）にもある。
  職員を無効にする、または `StaffListPage.tsx:60` の削除を行うと、**過去の月の勤務表・印刷・市の提出様式から
  その人の行が消える**（勤務表のデータ自体は `schedules` に残る）。監査で過去の月を出し直すときに困る。
- やること:
  1. 月を表示する画面（シフト表・印刷・Excel出力・TimePro・市の提出様式）では、
     「有効な職員」に加えて「その月の勤務表（通常行・兼務行）に1日でも入力がある職員」を出す。
     無効の職員は名前の横に「（退職）」などの印を付け、自動生成の対象には入れない（現状どおり）。
  2. 職員の削除は、どこかの月の勤務表に入力がある場合は止め、「無効にする」を案内する。
     入力がまったく無い職員だけ削除できる。
- やらないこと: 退職日の項目追加（要望が出たら別途）。過去データの書き換え。
- 完了条件: 無効にした職員が、勤務のある過去の月では表示・出力され、勤務の無い月では出ない。テストを追加。

### A3. 使用中の勤務パターンを削除できてしまう

- 根拠: `ShiftPatternsPage.tsx:61` の削除は、システム固定かどうかしか確かめない。
  勤務表・条件・職員の「可能な勤務」・設定（夜勤の前日の勤務など）が参照していても消せ、
  消すと過去の勤務表のマスが空欄になる。Excel 取込側には「使用中は削除不可」の判定が既にある。
- やること: 削除前に参照を調べ、使われていれば止めて、どこで使われているかを表示する
  （Excel 取込の判定を共通の関数にして使い回す）。
- 完了条件: 使用中のパターンは削除できず、理由が表示される。未使用のパターンは従来どおり削除できる。

### A4. 編集ロックを、古い画面からすり抜けて変更できる

- 根拠: 編集ロックの判定は画面の状態（`ShiftGridPage` の `canEditMonth`）だけ。
  `lib/firestore.ts` の書き込み（`setAssignment`・`setSecondaryAssignment`・`setLock`・`clearAllLocks`・
  `setEvent`・`saveMonthlyMaxDaysOverride`・`adoptCandidate`）はロックを見ない。
  ロックをかける前から開いていた別のタブ・別の人の画面は、再読み込みするまでそのまま書き込める。
- やること: 上の書き込みを「読んでから書く（トランザクション）」1回にまとめ、`editLock` があり、
  呼び出し側が一時解除中でなければ、専用のエラーを投げる。画面はエラーを受けて
  「この月はロックされました」と出し、読み込み直す。
  あわせて、今は1マスの入力ごとに「表があるか確認（トランザクション）→ 更新」の2往復になっているのを1往復にする。
- やらないこと: `firestore.rules` でのパスワード検証（目的は「うっかり防止」と設計書 §17 で決めてある）。
- 完了条件: ロック後、古い画面からの入力が保存されず、案内が出る。一時解除中は従来どおり保存できる。

### A5. 試験用（dev）と本番の見分けが付かない

- 根拠: 引き継ぎ書に「ユーザーが dev を見て『勤務が消えた』と驚いた」とある。画面上に環境の表示が無い。
- やること: 接続先が dev（`firebaseStatus.projectId === 'kaigo-shift-saas'`）のとき、
  画面の上に「試験用の環境です（本番のデータではありません）」の帯を出し、サイドバーの色も変える。
  本番では何も出さない。
- 完了条件: dev だけ帯が出る。印刷には出ない。

### A6. 画面の描画でエラーが出ると、真っ白になる

- 根拠: エラー境界（Error Boundary。画面の一部が壊れても全体が白くならないようにする仕組み）が無い。
- やること: ルートに1つ置き、「エラーが起きました。再読み込みしてください」とエラー内容を表示する。
- 完了条件: わざとエラーを起こしても、白い画面にならず案内が出る。

## 2. 優先度B：自動生成の質と体感（効果が大きい。計測しながら進める）

### B0. 先に「計測の土台」を作る（B1〜B5 の前提）

- 理由: 生成は乱数を使うため、1回の結果では良くなったか分からない。現状は比較の手段が無い。
- やること:
  1. 乱数を差し替えられるようにする（種を渡すと毎回同じ結果になる乱数を `GenerateInput` 経由で渡す。
     未指定なら従来どおり `Math.random`）。`sort(() => Math.random() - 0.5)` のような並べ替えは、
     結果が実行環境で変わるので「先にシャッフル → 安定した並べ替え」に置き換える。
  2. 4施設の形（夜勤→公休直行／明出→公休＋夜勤前日の決まった勤務／男女別人数／明休＋後回しの勤務）を
     まねた**架空の**データを `__tests__/fixtures` に作る（実名・実データは入れない）。
  3. 種を10個ほど変えて回し、必須違反・推奨未達・総合点・充足率の平均と最悪値を表にする
     スクリプト（`npm run bench`）を作る。
- 完了条件: 同じ種なら同じ結果になるテストがある。`npm run bench` で現状の数字が出る（この数字が以後の比較の基準）。
- 注意: 乱数の差し替えで既定の動き（確率的な性質）が変わらないこと。既存テスト107件が通ること。

### B1. 生成を裏で動かす（Web Worker 化）＋進み具合の表示

- 根拠: `generate()` は画面と同じスレッドで動く（`ShiftGridPage.tsx` の `handleGenerate`）。
  1案あたり 修復 最大1.5秒＋組み合わせ修復 最大0.5秒 ×2回＋探索0.8秒で、3案だと最悪10秒以上、画面が固まる。
  引き継ぎ書にも「生成中はページが固まる」とある。
- やること: `src/domain/scheduler/` は React / Firestore を import していないので、そのまま Worker で動かせる。
  入力を渡して結果を受け取る薄い Worker を作り、画面には「案A 作成中…（1/3）」と中止ボタンを出す。
  Worker が使えない環境では従来の動きに戻す。
- 完了条件: 生成中も画面が操作でき、中止できる。結果は従来と同じ形（`Candidate[]`）。

### B2. 探索の1手を軽くする（いちばん効く見込み）【計測済み】

- 根拠: `hillClimb.ts:65` の `evaluate()` は、1手ごとに `checkMonth`（全職員・全日・全ルール）と
  `scoreGrid` を丸ごとやり直す。合成データ（20名×30日）で **1回 約0.9ms、800ms で約900手**しか試せない。
  600マスある表に対して手数が少なすぎ、結果が運に左右される。
  特に `check.ts:36` は、違反が無くてもルール×日ごとに説明文（`ruleText`）を組み立てている。
- やること（効果の大きい順。1つずつ計測して採否を決める）:
  1. 件数だけを数える軽い評価を用意する（文章を作らない・配列に積まない）。
     `checkMonth().hardCount` と必ず一致することを、乱数で作った表で確かめるテストを付ける。
  2. `evalRuleDay` の説明文は、違反があったときだけ作る。
  3. ルールごとの対象日・職員ごとの上限・相性の表など、探索中に変わらないものは最初に1回だけ作る。
  4. （余力があれば）動かしたマスに関係する日・職員だけを数え直す差分評価。
- 完了条件: `npm run bench` で、同じ時間あたりの手数が5倍以上。必須違反の平均が現状より悪くならない。

### B3. 時間いっぱい「作り直して良い方を残す」

- 根拠: 今は1案につき1回しか作らない。最初の割り当て（夜勤→日中）は運で良し悪しが分かれる。
- やること: B1 の後、1案あたりの持ち時間（例: 5秒。設定で変更可）の中で何度か作り、
  「必須違反が少ない → 総合点が高い」順でいちばん良いものを残す。
- 完了条件: bench で必須違反の平均・最悪値が改善。持ち時間は `settings/generationConfig` で上書きできる。

### B4. 夜勤の入れ替えを探索に加える（先に計測して要否を判断）

- 根拠: `hillClimb.ts` の3種類の手は、どれも夜勤と明を動かさない（137〜138行ほか）。
  夜勤は最初の割り当て（`generateOne.ts` の「2. 夜勤割当」）で決まったきりで、
  夜勤回数の目標とのずれ（公平の採点に入っている）を後から直せない。
- やること: まず bench で「夜勤回数の目標とのずれ」を数字で出す。ずれが目立つ施設の形があれば、
  同じ日の夜勤を2人の間で入れ替える手（明・翌日の公休・前日の決まった勤務をひとまとめで動かす）を追加する。
  ロック・希望休・`canWork` の決まりは必ず守る。
- 完了条件: 追加する場合、夜勤回数のずれが改善し、必須違反が増えない。改善が無ければ追加しない（記録だけ残す）。

### B5. 受け入れ方の改良（LAHC など）は最後に

- 保留中の項目。B0〜B3 の後、bench で比べて効果があるときだけ入れる。
  あわせて、現状は「必須違反の件数 → 総合点」だけで比べていて推奨未達の件数を見ていない点も、ここで検討する。

## 3. 優先度C：使いやすさ

### C1. まとめて入力（対象外の職員の手入力を楽にする）

  今は1マスずつクリックして選ぶしかない。
- やること: シフト表に「まとめて入力」を追加。職員（複数）・曜日（平日／土日／曜日指定）・勤務パターンを選び、
  **空いているマスだけ**に入れる（ロック済み・入力済み・希望休の日は飛ばす。件数を確認してから実行）。
- 完了条件: 事務職員の「平日は B1」が数クリックで入る。1回の書き込みにまとめる。

### C2. キーボードで入力・元に戻す

- やること: マスを選んで矢印キーで移動、記号の頭文字（例: `B1`）を打って Enter で入力、Delete で消す。
  手入力は Ctrl+Z で元に戻せる（その画面を開いている間の履歴でよい）。
- 完了条件: マウスを使わずに1行入力できる。元に戻すとデータも戻る。

### C3. 違反の一覧から、そのマスへ飛べるようにする

- 根拠: 違反は文字の一覧（`checkResult.hard` の文字列）だけで、表のどこかを目で探す必要がある。
- やること: 違反を「職員・日・種類・文章」を持つ形で返すようにし（文字列の一覧は互換のため残す）、
  一覧を職員別／日別にまとめ、クリックでそのマスまでスクロールして光らせる。

- 完了条件: 違反をクリックすると該当のマスが見える位置に来る。

### C4. ほかの人の変更に気づけるようにする

- 根拠: 読み込みは開いたときの1回だけ（`onSnapshot` 不使用）。2人が同じ月を開いていると、相手の入力が見えない。
  マス単位の保存なので上書き事故は起きにくいが、古い表を見て判断してしまう。
- やること: 表示中の月の勤務表だけ、変更を受け取って画面に反映する（Firestore の読み取り回数が増えるので、対象は1文書だけ）。
- 完了条件: 2つの画面で同じ月を開き、片方の入力がもう片方に数秒で出る。

### C5. 確認の箱を統一（低優先）

- `confirm()` / `alert()` が19か所ある（ブラウザ標準の箱で、見た目が合わず、長文が読みにくい）。
  D1 の見た目の整理のときに、アプリ内の確認ダイアログへ置き換える。

## 4. 優先度D：見た目の刷新（「見やすく・おしゃれに」）

方向性は **今の落ち着いた緑（`#1d7a63` / `#0c4a3b`）と生成りの背景を活かし、情報の強弱と一貫性を整える**。
色やフォントを大きく変えるのではなく、「どこを見ればよいか」がすぐ分かる画面にする。
**着手前に、D2〜D4 の完成イメージをユーザーに見せて了承を取ること**（好みが分かれるため）。

### D1. 配色と部品の土台をそろえる（見た目は変えない下準備）

- 根拠: `App.css` は1742行で、色の直書きが34種類・変数（`var(--…)`）は0。`style={{…}}` の直書きが117か所。
- やること: 色・角の丸み・余白・影を CSS 変数にまとめる（例: `--color-primary`、`--color-border`、`--radius-md`）。
  ボタンは「主ボタン（緑の塗り）／通常／文字だけ／危険」の4種類に統一。`App.css` を画面ごとのファイルに分ける。
- 完了条件: 画面の見た目が変わらない（主要画面を前後で見比べる）。色の直書きが変数の定義以外に残らない。

### D2. アイコンを絵文字から線のアイコンへ

- 根拠: サイドバーとボタンが絵文字（📅🙋🌴…）。Windows では絵文字が重く見え、大きさ・色がそろわない。
- やること: 線のアイコン集（`lucide-react` を想定。新しい依存として設計書に理由を書く）へ置き換える。
- 完了条件: サイドバー・ツールバー・メニューの絵文字が無くなり、選択中は緑、その他は灰色でそろう。

### D3. サイドバーを整理する

- 根拠: 12項目が同じ重みで縦に並ぶ（`FacilityShell.tsx` の `TABS`）。毎月使うものと、最初に1回設定するものが混ざっている。
- やること: 3つのまとまりに分ける。
  - 毎月の作業: シフト表／希望休／有給休暇
  - 施設の設定: 職員／相性／条件／勤務パターン／職種／雇用区分／設定
  - データ: Excel入出力／旧データ取込
  幅を広げて「アイコン＋文字」を横並びにし、折りたたむとアイコンだけになる。URL は変えない。

### D4. シフト表を読みやすくする（いちばん効果が大きい）

  1. 土曜・日曜の**列全体**にごく薄い色を敷く（今は見出しの文字色だけ）。今日の列を緑の枠で示す。
  2. 週の区切り（月曜の左）の線を少し濃くする。

  6. 違反・希望休の印の説明（凡例）を、表の下の長い文章から、表の上の小さな凡例に変える。
- 注意: 列の固定・横スクロールバー常時表示・「画面に収める」・印刷（`PrintableShiftGrid`）の動きを変えない。
- 完了条件: 上の6点が入り、印刷結果が従来と同じ。

### D5. 3案の比較カードを見やすく

## 5. 優先度E：保守と安全（時間のあるときに）

| 番号 | 内容 | 根拠・補足 |
|---|---|---|
| E1 | `firestore.rules` の自動テスト | 個人情報を守る要のルールにテストが無い。エミュレーター（Java が必要）で「他法人・未所属・管理者以外は読めない／書けない」を確かめる |
| E2 | 配信時の安全用ヘッダー | `firebase.json` に `X-Content-Type-Options`・`Referrer-Policy`・ほかのサイトへの埋め込み禁止を追加 |
| E3 | 初回表示の軽量化 | 本体のファイルが 1,006 kB（圧縮後 298 kB）。施設・ユーザー管理や設定系の画面を「開いたときに読む」形にする。業務用PCなので優先度は低い |
| E4 | push 時の自動チェック（CI） | `.github/` が無い。push のたびにテスト・lint・ビルドを自動で回す。ユーザーの GitHub 設定が要る |
| E5 | 古いコメントの修正 | `lib/firebase.ts` の冒頭が「`.env.local` から読み込む」のまま（実際は `.env.development` / `.env.production`） |
| E6 | モーダルの操作性 | `Modal.tsx` に `role="dialog"` とフォーカスの閉じ込めが無い。D1 のときに合わせて直す |

### ユーザーの判断が要るもの（勝手に実装しない）

- 一定時間操作が無いときの自動ログアウト（施設の共用PCで使うなら検討）。
- タブレットでの利用。使うなら、右クリックでのセルのロック（タッチでは出せない）の代わりの操作が要る。
- 編集ロックのパスワードは4文字以上で、変換した値は施設の職員なら読める場所にある。
  「うっかり防止」が目的なら現状でよい。改ざん防止まで求めるなら別の仕組みが要る。
